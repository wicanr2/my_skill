# 共同決策訪談（`grill-me`）

把 `grill-me` 當成「使用者掌握價值取捨、agent 負責查證與整理」的工作模式。目標是達到可辯護的共同理解，不是快速產生一份看似完整、其實由 agent 私自決定的方案。

`grill-me` 是使用者可直接指定的入口；`~/.codex/skills/grilling/` 是可由 agent
自動啟動的共用核心。兩者採同一套決策樹、事實／決策分離與確認閘門；若某個
session 沒有載入 `grilling`，本檔仍可獨立完成訪談，不把技能相依性當成使用者
需要自行排除的問題。

本機整合 `~/.claude/CLAUDE.md` 的互動偏好：若確實存在會影響正確執行的問題，
先問使用者；若問題只是可由檔案、原始資料、測試或可靠來源查出的事實，先自行
查證，不把查資料偽裝成決策題。GitHub 上游把 `grill-me`（使用者入口）與
`grilling`（可自動啟動的核心）分開；本機保留這個分工，並因繁中閱讀與本專案的
交接習慣預設一題一答。使用者明確要求批次時，才把同一前沿中互不相依的問題
合併提問。

## 先判斷是否需要啟動

直接執行可逆、低風險、已獲明確授權的搜尋、整理、測試、文件修正與實作。
啟動訪談並暫停依賴該決定的分支，若工作會實質改變：

- 產品目標、範圍、玩家體驗或完成標準；
- engine／game-pack 邊界、API、JSON schema、save 相容性或資料來源；
- 原版忠實度、GUI／字型／動畫／音訊與美化取捨；
- 授權、公開素材、發行平台、影片、捐款或其他對外承諾；
- 破壞性操作，或需要把假說寫進正式規則、程式與玩家可見內容。

不因每個小實作都提問。可以由檔案、程式碼、bytes、實機、測試、可靠網頁
或隔離 subagent 得知的事實，先自行查證；不要把查資料的責任丟給使用者。

## 決策樹、前沿與輪次

先把根決策及其依賴畫成設計樹。父節點未決定前，不要提前詢問只依賴它的
子節點；每次回答後重新計算「前沿（frontier）」：只保留前置決策已確定、
現在真的會阻塞工作的節點。若新答案改變父節點，重新開啟受影響的子分支，
不能沿用舊假設。

預設每輪只問一題，適合需要慢慢閱讀與確認的對話。只有使用者明確要求批次
回答時，才可在同一輪列出多個互不依賴的前沿問題；依賴關係未解決的問題必須
留到下一輪。無論採哪種節奏，都不能把整棵樹一次倒給使用者。

## 問題格式

每個問題都先給足背景，最後只留下單一待回答事項：

1. **目前已知事實**：列出檔案、bytes、實機、測試、網路或推論證據，明確標示
   `exact／strong inference／hypothesis／unknown`。
2. **現在為何需要決定**：指出會解鎖或暫停的工作分支。
3. **真正不同的選項**：說明取捨，不用假選項湊數。
4. **agent 建議**：明寫「建議」，附一個簡短理由；建議不是使用者授權。
5. **實際影響**：交代時間、相容性、維護、忠實度、風險與可逆性。
6. **單一問題**：請使用者選擇、補充，或回答「不知道」。

使用者回答後，先用一句話重述：「採用什麼、排除什麼、哪些分支繼續或暫停」，
再做不依賴新決定的安全工作；不要在重述前偷偷開始依賴該答案的實作。

## 不替使用者作決定

- 使用者說「不知道」是真實答案。把它標為未知，改做小型 prototype、查證或提出可撤回的實驗，不把沉默或含糊回覆解讀成同意。
- 訪談中不能自行選定產品方向、原版語意、公開授權或美化取捨。可繼續做不依賴該決定的安全工作；依賴該決定的分支標為 `pending` 並停止。
- 若新證據推翻既有決定，保留舊證據與訂正理由，重新打開受影響的父節點；不要默默把推測改寫成需求。
- 不要把「好」「可以」「繼續」自動解讀為尚未呈現過的重大取捨已獲確認；若答案含糊且會改變方向，先指出歧義並只問最小必要澄清。
- 「go」「continue」「繼續」只能授權已明確確認的分支與不依賴決策的安全工作；
  若目前仍有未向使用者展示的重大前沿，必須先提出那一題，不能把催促進度當成
  對原版語意、架構、資料格式或發行方向的默認同意。
- 主動指出風險與反對理由。使用者沒有反對，不等於已理解或同意；要讓使用者能說明為何採用該選項。

## 事實、決策與確認閘門

- 事實是 agent 的工作：先讀 `AGENTS.md`、`CONTEXT.md`、ADR、spec、程式碼、
  原始資料與可用外部來源。若需 subagent，只派它查證資料，不派它代替使用者
  決定產品價值。
- 決策是使用者的工作：agent 可以推薦與整理影響，但不能因「看起來合理」、
  沉默、既有 prototype 或單一截圖而自行定案。
- 前沿清空後仍不能直接實作。先列出「採用、排除、仍未知、受影響檔案／分支」
  的共同理解摘要，等待使用者確認；確認前只做獨立的查證與可丟棄 prototype。
- 確認後若決策會影響專案，於同一重大 milestone 更新 `CONTEXT.md`、ADR 或
  適當 spec，記錄依據、推論等級、排除選項與受影響分支。一般 stateless
  `grill-me` 不自行留下工作樹檔案。

## Remake 專案的決策閘門

對 Gold Box／老遊戲 remake，以下事項預設需要使用者參與：

- 是否改變原版行為、地圖、規則、戰鬥演出、中文字體密度或 GUI 版面。
- 是否把某項假說寫進 engine schema、JSON、正式規則或玩家可見內容。
- 是否新增作品中立 engine 能力，或把功能留在 CoAB game-pack。
- 是否採用美化 theme、刪除／覆蓋原始素材、調整平台支援或改變 save 相容性。
- 是否改 license、公開資產、發布套件、影片、完成聲明或其他不可逆／對外承諾。

在上述事項上，先列出原版證據與 `exact／strong inference／hypothesis／unknown`，再問價值取捨；不能用「目前能跑」代替使用者對方向的決定。反組譯仍採可玩性優先、證據最小充分：功能證據已足以實作並驗證後，停止深挖與玩家路徑無關的函式。

對 Golden Box remake 特別檢查：

- 原版忠實 theme 與美化 theme 是否分離；不能以美化 prototype 偷換驗收基準。
- engine 能力是否作品中立，劇情、文字、座標、怪物與翻譯是否留在 JSON/game-pack。
- `hypothesis` 是否被誤寫成正式 schema、規則、測試期望值或玩家可見內容。
- 是否把「解碼器能讀」「單張截圖」「direct-entry」誤報為完整可玩、完整戰鬥
  或可通關。

## 視覺與操作取捨

「看起來如何」「手感如何」「哪個版面較好」不能靠口頭推演完成。若選項需要
實際反應，先做最小、可丟棄、可並列比較的 prototype／截圖／操作片段，再請
使用者選擇；prototype 不得直接變成正式資產或驗收證據。

## 訪談結束與記錄

- 一般共同決策對話預設不新增檔案，避免把未確認的想法固化。
- 一旦使用者確認會影響專案的重大決定，在同一 milestone 更新專案的 `CONTEXT.md`、ADR 或適當 spec，並記錄採用選項、排除選項、依據與受影響分支。
- 只有在前沿清空、使用者已確認共同理解、每個採用選項都能說明取捨、且沒有未標示的重大假設時，才把訪談結果交給實作或 `to-spec` 類工作。
- 訪談不等於完成：實作仍須依規格、測試、正常玩家路徑與證據完成驗證。

如果訪談反覆延長，先縮小範圍到一個可交付 vertical slice；不要用重述同一問題
代替新證據，也不要以固定問題數硬截斷真正尚未解決的父節點。使用者可以明確
說「先接受目前理解」「先做 prototype」或「停止訪談」，agent 應記錄剩餘未知
並依該邊界行動。
