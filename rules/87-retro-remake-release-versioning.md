# 復古 remake 的 version-date 正式版號（2026-09-01 定案）

**這是已經定案的 `[HARD]` 規則，不要每個專案重問一次。** 正式版號固定為：

```text
v.<主版>.<次版>.<修訂版>-YYYYMMDD
```

例如 `v.1.0.0-20260901`。開頭是字面值 `v.`；不可寫成 `v1.0.0-20260901`、
裸日期 `20260901`、`20260901.1` 或在日期後追加 `-r2`。

## `[HARD]` 機器驗證

所有打包、驗包、更新檢查與發布入口都使用完整比對，失敗即關閉：

```regex
^v\.[0-9]+\.[0-9]+\.[0-9]+-[0-9]{8}$
```

不可在未帶參數時默認產生裸日期。

## `[HARD]` 七處必須完全一致

1. Git tag；
2. GitHub Release 標題與發行說明；
3. 程式顯示的版本字串；
4. `dist-all/<版本>/`；
5. 各平台封包檔名；
6. manifest 與 SHA-256；
7. README／CONTEXT／WORKLOG 的正式交付連結與紀錄。

日期採專案明定時區；沒有明定時不得猜。同日重發提高三段版本中的修訂號，例如
`v.1.0.0-20260901` 的修正版是 `v.1.0.1-20260901`。

## 已發布版本與撤回

已發布的 tag／Release 預設不可移動、覆寫或刪除。只有使用者明確指定撤回錯誤版號時：

1. 精確確認舊 Release 與 tag；
2. 刪除指定的 GitHub Release 與遠端 tag；
3. 回讀確認舊 tag 不存在，並刪除本機失效 tag，避免誤推回；
4. 從乾淨輸入建立合規的新版本；
5. 驗證封包、manifest、SHA-256、正常啟動與權利邊界；
6. 建立新 tag／Release 並回讀公開資產。

固定版號規則不構成刪除授權；沒有使用者明確指示時，必須保留歷史 Release。
