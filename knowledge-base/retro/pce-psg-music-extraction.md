# PC Engine：把原版音樂與音效弄出來給 remake 用

適用：HuCard 遊戲的 remake／中文化，需要原版配樂或音效。
姊妹篇：`megadrive-vgm-music-extraction.md`（Mega Drive）、`pce-huc6280-re-toolkit.md`（逆向工具鏈）。

## 為什麼 PC Engine 比 Mega Drive 好處理

Mega Drive 要面對 68000 + Z80 雙 CPU、YM2612 FM 合成、外加 PSG，音樂驅動常常整包在
Z80 RAM 裡。PC Engine 沒有這些：**PSG 就掛在 HuC6280 的 I/O 頁上，主 CPU 直接寫**。

所以第一步永遠一樣、而且一定會中：**對 PSG 的埠設寫入監看。**

## 一、PSG 的埠（記住這十個位址就夠開始）

MPR0 = `$FF` 時，I/O 頁在 `$0000`–`$1FFF`，PSG 在 `$0800`–`$0809`：

| 埠 | 內容 |
|---|---|
| `$0800` | 選聲道（0–5） |
| `$0801` | 主音量：bit 7–4 左、3–0 右 |
| `$0802`／`$0803` | 12-bit 週期（低 8 / 高 4） |
| `$0804` | bit7 啟用、bit6 DDA、bit 4–0 聲道音量 |
| `$0805` | 左右音量：bit 7–4 左、3–0 右 |
| `$0806` | 波表資料，5 bit，寫一次前進一格，32 格一圈 |
| `$0807` | 雜訊，**只有聲道 4、5 有** |
| `$0808`／`$0809` | LFO（聲道 1 調變聲道 0） |

音高 = `3579545 / (32 × 週期)`，週期 0 當 4096。

**判讀捷徑**：如果你的監看看到雜訊埠 `$0807` 只在聲道 4、5 被寫，那就對了——
硬體上也只有那兩個有雜訊。看到別的聲道也寫，八成是你的聲道追蹤寫錯了。

## 二、找驅動：一次 probe 就定位

Mesen2 headless Lua，`emu.addMemoryCallback(fn, write, 0x0800, 0x0809, pce, pceMemory)`。
記下命中的 **PC 與 MPR 快照**——MPR 那一欄才是答案：PC 落在哪個視窗，
就查對應的 MPR 槽，那個值就是驅動所在的實體 bank。

> **實體 bank 不等於 `bank × 0x2000`。** 有些 HuCard 的 bank 編號中間有洞
> （例如 `$00`–`$1F` 接 `$40`–`$4F`，384 KB 的卡）。用錯會越界，或更糟——
> **落在別的資料上反組譯出一段自洽但完全錯的程式碼**。反組譯前先確認卡的 bank 佈局。

樂曲資料通常在**另一個** MPR 槽，而且會在播放中切換。**盯著哪一個 MPR 槽的值在變，
那就是樂曲 bank。**

## 三、兩條路，先想清楚要哪一條

| | 錄 VGM | 解樂譜 |
|---|---|---|
| 拿到 | 那一次播放的完整埠寫入 | 每首曲子、每個音效，各自獨立 |
| 拿不到 | 沒觸發到的曲子；音效混在音樂裡；沒有樂譜語意 | — |
| 成本 | 一支 Lua + 一顆 PSG 合成器 | 上面全部 ＋ 序列器與資料格式的逆向 |
| 適合 | 做 demo、推廣片、先聽聽看 | 正式 remake、要做音效、要互動式配樂 |

**先問「要不要每一首都拿到」。** 要，就沒有捷徑，得解樂譜——因為錄音只錄得到你有辦法
在遊戲裡觸發的東西，而且音效會蓋在音樂上分不開。

## 四、錄 VGM 的做法（含兩個會安靜出錯的坑）

VGM 本來就支援 HuC6280：命令 `0xB9 port data`，header 偏移 `0xA4` 放 PSG 時脈
（3579545）。所以只要把埠寫入照順序記下來，任何 VGM 播放器都能播。

**時間軸用幀邊界，不要用 CPU cycle。** 這類驅動幾乎都是 VBlank 同步（每幀跑一次），
而 VGM 的 `0x62` 正好是「等 1/60 秒」。用 cycle 反而要在每次埠寫入的熱路徑上取 CPU 狀態——
PSG 每幀寫入上百次，headless run 會逾時。

> **坑 1：一定要從第 0 幀開始錄。** 主音量、LFO 與大部分波表上傳都在**開機初始化**
> 就寫完了。從中途開錄，這些一筆都沒有，播出來是錯的音量甚至無聲——
> **而 VGM 檔本身看起來完全正常**：大小合理、命令齊全、聲道分佈漂亮。
> 檢查法：解析回來數 `$0801`／`$0806`／`$0808` 的寫入次數，是 0 就是漏了初始化。

> **坑 2：錄到的是「那一次播放」，不是樂譜。** 同一首曲子在不同遊戲狀態下可能變速、
> 疊音效、或根本沒被觸發。要寫「這是第 N 首曲子」之前，先確認你是怎麼觸發它的。

## 五、拿 oracle 音訊來裁決合成器

PSG 的**音量曲線**是最容易憑記憶寫錯的一塊（幾個欄位怎麼疊、每階幾 dB），
而公開文件寫得含糊。不要猜——**量**：

```bash
mednafen -sounddriver dummy -soundrecord out.wav game.pce
```

Mednafen 的 `-soundrecord` 直接吐 WAV。於是你有一組完美的對照：
**VGM 是精確的輸入（暫存器寫入），WAV 是精確的輸出**。合成器寫完拿這兩者對照，
音量曲線對不上一眼就看得出來。

比對時**不要要求逐 sample 相同**：模擬器有自己的重取樣與低通濾波，
逐 sample 比只會量到濾波器的差別。要比的是：主要頻率隨時間的軌跡、音符起始時間、
各段落的 RMS 比例。

## 六、解樂譜的入口

從驅動往下找這三層，順序不要顛倒：

1. **每 voice 的狀態陣列**（頻率低／高、音量、左右音量……並排在 RAM，用 X 索引）。
   對它們設寫入監看 → 找到序列器的 setter。
2. **setter 的呼叫端** = 真正讀樂譜的迴圈。對它設**讀取**監看，量出 score 的實際位址——
   **不要從「這張表長得像指標表」往回猜**。ROM 裡長得像指標表的東西太多了。
3. **曲目表**：score 位址往回找誰算出它。

會遇到「voice 數量比硬體聲道多」（例如 12 個 voice 對 6 個聲道），那通常是音樂與音效
各一組、混完才寫硬體——但**那是假說，要有證據才能寫成結論**。

## 七、授權（每次都要想一遍）

錄出來的 VGM／WAV／OGG 都是**原版配樂的衍生資料**，與解碼後的圖形資產同級：
本機產生、不進版控、不進 release。

而「把原版音樂放進對外的推廣影片或產品」是**授權決定，不是技術決定**——
技術上做得到不等於可以散布。要對外，通常得另外配新曲。
