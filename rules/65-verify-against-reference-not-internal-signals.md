# 有 ground truth 的專案:驗收=對 reference 實測,不是內部訊號(測試綠會一路謊報完成)

> 觸發:任何「有明確正確答案(reference)」的長專案 —— port / remake / 遷移 / 重寫 / 對齊某規格或原版。
> 尤其**用 agent/subagent 大量產出、跨多輪**時。與 `60`(先建可驗證訊號)、`62`(靜態溯源)、
> `63`(truth-in-code、別信 stale marker)、`64`(截圖 oracle)、`82`(port 驗證)、`83`(完整性)同源;
> 本檔補的獨特角度是**元認知**:為什麼 AGENT 特別容易「說完成了其實沒有」,以及對策的優先序。

## 核心洞見(第一性原理)

agent 的獎勵訊號幾乎都是**內部的**:編譯過、測試綠、`git diff` 乾淨、vet clean、subagent 回報「完成」。
這些全給正回饋,卻**只反映內部自洽,不反映「對 reference 一致」**。「對 reference 一致」是**外部訊號**,
要主動建閉環才拿得到。缺這個閉環時,agent 會沿內部訊號一路「完成」下去——**越自洽越自信,離目標卻不一定更近**。

→ 真實案例(retro remake,2026-07):子系統全移植、對拍測試全綠、還打包了可玩檔=帳面「完成」;
但玩起來完全不是原版,整個「流程驅動層」缺席,「可通關」是 debug 捷徑串出來的假象。**多輪反組譯燒掉約一個月 token,
才被使用者花五分鐘實測戳破**。

## 硬規則

- **[HARD] 「測試綠」是「零件對」,不是「東西能用」。** 有 reference 的專案,宣稱任何「X 完成」前,
  問一句:**一個終端使用者、不碰任何後門,能實際走到/用到 X 嗎?** 不能就不算完成。
- **[HARD] oracle 有優先序,reference 實機 > agent 宣稱:**
  `(0) 人親自實測 > (1) reference 實機/錄影/原版 > (2) 文件/攻略/規格 > (3) agent 的分析/RE 宣稱`。
  **agent 的宣稱一律不當完備**;每個機制動手修**之前**,先用 reference 跑一次那個機制(便宜、一次見效)。
- **[HARD] debug/後門串起來的「能跑完」不算能跑完。** 把每個 debug hook / env 捷徑 / 測試專用注入
  列成待移除清單,驗收時全部拔掉重跑。
- **UI/視覺產物一律 dump 出來肉眼比對 reference**,不信「測試綠/應該會動」——常抓到「資料對但顯示錯」
  (如字元對應表誤標)這種測試照樣綠的 bug(配 `64` 截圖 oracle)。

## 對策 / How to apply

- **人的實測回報 = 最高優先的 spec 來源。** 使用者花幾分鐘實際用一下、回幾個症狀,常一發就讓根因定案,
  勝過 agent 很多輪自動分析。當黃金訊號,不是打擾;主動請使用者實測。
- **深挖前先問方向:** 「這是往『對 reference 一致』,還是只是讓某機制內部自洽?」後者投報低,
  登進 worklist 待辦即可,別無限鑽(這是燒 token 最兇處)。
- **先確定 spec 齊了才動手,不邊做邊挖。** spec 齊(reference 行為已定、資料已定位)時實作又快又省;
  沒齊就動手 = 邊做邊猜邊燒。深挖只在「往驗收方向」時才值得。
- **進度真相放單一來源**(code + 一份 GAP/FLOW 清單),不放「某輪對話說完成了」(配 `63`)。
- **subagent 交回一律協調者獨立核實**(重跑測試 + 看 diff + 抽查關鍵邏輯 + 視覺 dump)才收;
  模型越便宜、輪數越多,這條越不能省(配 `45`)。

## 為什麼防護值得

不防的代價不是「多花一點工」,是「沿內部訊號往錯方向深挖,燒掉一個月 token 還原地打轉」。
防護成本極低(reference 實測一次)。**把外部訊號接進迴圈、並讓它的優先序高於一切內部訊號**,
是有 ground truth 專案的第一要務。
