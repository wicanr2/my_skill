# 共同決策核心（`grilling`）

把本技能當成可重用的共同決策訪談核心：使用者掌握價值取捨，Codex 負責查證
事實、整理依賴、提出建議與揭露風險。重大方向未確認前，不把自己的建議當成
使用者授權，也不直接把假設寫入正式程式、規格或對外承諾。

## 啟動門檻

當工作會實質改變下列任一項時，先啟動訪談並暫停依賴該決定的分支：

- 目標、範圍、完成標準、玩家體驗或正常玩家路徑；
- engine／game-pack 邊界、API、JSON schema、save 相容性或資料來源；
- 原版忠實度、GUI／字型／動畫／音訊、美化 theme 或平台支援；
- 授權、公開素材、發行套件、影片、捐款或其他對外承諾；
- 需要把未證實假說變成正式規則，或不可逆／破壞性的操作。

低風險且已獲明確授權的搜尋、整理、測試、文件修正、可撤回 prototype 與
局部實作可直接做；不要為每個小改動打斷使用者。

## 決策樹與前沿

1. 先把根決策、依賴與可能受影響的分支列成樹。
2. 把前置條件已確定、現在真的會阻塞工作的節點稱為「前沿」。
3. 每輪只問前沿中最早、最能解鎖後續工作的單一問題；只有使用者明確要求
   批次回答時，才同輪提出互不相依的多題。
4. 使用者回答後，重新計算前沿；若父決策改變，重新開啟受影響的子分支，
   不沿用舊假設。

一次一題是本機預設，適合需要閱讀證據與逐步取捨的繁中／復古遊戲工作。
這是互動節奏，不是禁止批次：使用者要求加速時，可列出同輪互不相依的前沿，
仍不可把相依問題提前混在一起。

這是對上游「一輪詢問整個目前前沿」做的本機化選擇：若使用者未明確要求批次，
每輪只問一題，讓使用者能真正反駁、改寫或回答「不知道」；若使用者要求批次，
才採上游的前沿分輪方式，而且同一輪的問題必須彼此獨立。無論節奏為何，前沿
清空後仍要等待使用者確認共同理解，不能直接開始依賴該決定的實作。

## 事實與決策分離

- **事實由 Codex 查證。** 先讀規則、程式碼、檔案、bytes、runtime trace、
  使用者提供資料與可靠外部來源；可由工具找出的內容不要反問使用者。
- **價值決策由使用者確認。** 是否偏向原版、是否美化、是否擴充 engine、
  是否接受相容性／時間／維護成本，不能由「看起來合理」、沉默、既有 prototype
  或單張截圖代答。
- subagent 只負責收集與交叉驗證事實，不替使用者選產品方向。
- 每項結論標記 `exact`、`strong inference`、`hypothesis` 或 `unknown`；
  名稱、常數、單一 xref、攻略敘述或解碼器能讀取本身不能升格成已證實規則。

## 每題格式

先給足必要背景，最後只留一個待回答事項：

1. 已知事實與證據等級；
2. 為何現在需要決定、會解鎖或暫停哪個分支；
3. 真正不同的選項與取捨；
4. 明確寫出 Codex 的「建議」及短理由；
5. 交代時間、相容性、維護、忠實度、風險與可逆性；
6. 請使用者選擇、補充或回答「不知道」。

不要用假選項湊數。使用者回答「不知道」時，保留 `unknown`，改做查證或小型
可丟棄 prototype；不要把未知解讀成同意。

## 確認閘門

當前沿清空後，先輸出共同理解摘要：

- 採用什麼、排除什麼；
- 仍未知與其證據等級；
- 受影響檔案、模組、save／schema／發行分支；
- 哪些工作可繼續、哪些依賴確認。

在使用者確認共同理解前，只做不依賴決策的查證與可撤回 prototype，不把方案
實作成正式規則。收到明確確認後，先用一句話重述「採用、排除、繼續／暫停」，
再開始依賴該答案的實作。若只是「繼續」而前面沒有清楚呈現待確認的重大取捨，
不得擅自把它擴大解讀成所有未展示決策都已同意。

## 原版重製專案閘門

對 Gold Box／SSI 或其他老遊戲 remake，額外檢查：

- 原版忠實 theme 與美化 theme 分離；美化 prototype 不取代驗收基準；
- engine 只放作品中立能力，劇情、文字、座標、怪物與翻譯留在 JSON／game-pack；
- `hypothesis` 不進正式 schema、規則、產品測試期望值或玩家可見內容；
- 「解碼器可以讀」、單張截圖或 direct-entry 不得宣稱完整可玩、完整戰鬥或可通關；
- 逆向只追到足以支援已選定玩家功能的最小充分證據，與玩家路徑無關的函式不
  深挖；IDA 註記維持非破壞性，原始位址與證據等級永遠保留。

## 視覺與操作取捨

「哪個版面好看」「字級是否合適」「動畫是否要美化」先做最小、可丟棄、可並列
比較的 prototype／截圖／操作片段，再請使用者選擇。prototype 不自動成為正式
資產、layout spec 或完成證據。

## 決策後記錄

本核心預設是無狀態，不因每次訪談新增雜亂檔案。若使用者確認的決策會影響專案，
在同一重大 milestone 更新該專案的 `CONTEXT.md`、ADR 或適當 spec，記錄依據、
推論等級、採用／排除選項與受影響分支；不要在確認前寫入永久文件。
