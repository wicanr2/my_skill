# 白話寫作 (Plain Language) 定義與準則

定義「白話」是什麼、怎麼寫。配合 核心文風規則 文風總則使用;核心文風規則 規定「不要貼導引式 meta 標籤」(反面),本檔規定「白話到底該怎麼寫」(正面)。

## 什麼是「白話」

白話 = 讓**沒有該領域背景的人**(現場主管、客戶業務端、管理層)第一次讀就能抓到重點與結論的寫法。
白話是「**好文筆 + 低認知負荷**」,**不是**降低正確性,也**不是**貼「白話版」標籤。

## 七條準則 (寫白話時逐條套)

1. **結論先行 (BLUF)**:第一段 / 第一屏就講答案,讓人約 30 秒內掌握「發生什麼、結論、為什麼重要」。
2. **短句、常用詞**:一句一個意思;能用日常詞就不用術語;避免被動句與名詞化堆疊 (「進行優化」→「改快」)。
3. **術語即時翻譯**:每個專有名詞 / 縮寫第一次出現,當場用一句話或括號解釋,或集中在中性標題的「名詞說明」區;之後才直接使用。
4. **具體勝抽象**:用數字、實例、生活化比喻取代抽象描述;比喻要貼近讀者日常經驗。
5. **數據配「所以呢」**:每組數字 / 圖表後,緊跟一句白話結論 (這代表什麼、為什麼重要)。
6. **自然融入,不貼標籤,不自我描述**:白話說明寫成正文自然的開場與導言,**不用**「先看這段 / 用生活化方式說明 / 白話: / (白話版) / 30 秒看懂」這類 meta 標籤,**也不寫**「用途:客戶答辯」「讀者含非技術人員」「本報告供 XX 閱讀」這類描述文件目的/受眾的後設句,**也不用**「客戶問的是…」「本報告回答…」這類「誰問的/在回答什麼」框架句,**也不用**「本報告為單檔自包含 HTML/無外部資源/可另存 PDF」這類描述檔案格式/技術屬性的自述句(直接陳述分析與結論)(見 核心文風規則);章節用中性自然標題,讓讀者不知不覺進入狀況。
7. **不犧牲正確性**:簡化用語可以,但數字 / 結論 / 領域用詞 (專案術語、狀態碼、任務 ID 等) 一字不改;白話與精確並存,衝突時正確性優先。

## 何時用

- **對外 / 客戶 / 管理層交付、跨團隊溝通、需要非技術讀者理解**的報告與簡報:七條全套。
- 內部純 RD 技術文件:可保留較多術語,但第 1 / 5 / 6 / 7 條仍適用。
- 需要同時有「技術版」與「白話版」時:用**檔名**區分 (如 `_plain`),不要把「白話」字樣寫進可見內容。
