## `[HARD]` 動手時機：第一個公開 commit 之前

跟「先確認 `git config user.email`」是同一個時機（先確認 commit 作者身分的同一時機）。
**不要留到發行前**——在那之前每一次 push 都是沒有條款的公開散布，
而事後補條款管不到已經拿走的副本。

## `[HARD]` 授權要出現在四個地方

| 位置 | 為什麼 |
|---|---|
| repo 根目錄 `LICENSE` | GitHub 靠這個檔名顯示授權；缺了就等於「未授權」 |
| README 的「授權、致謝與聲明」段（[`80`](80-retro-cht-readme-polish.md) 骨架第 9 項）| 摘要 ＋ 指向 `LICENSE`，順便講清楚不涵蓋原版素材 |
| **每一個發行包裡** | ⭐ 拿到 `tar.gz` 的人**看不到儲存庫**。包裡沒有這一份，收到的人就不知道自己被授權了什麼——而條款自己要求散布時保留全文 |
| 發行根目錄（`dist-all/` 之類）與 AppImage 的 `usr/share/doc/` | 同上；打包腳本要把它複製進去，不要靠人記得 |

⚠ **APK 是例外，要另外想辦法**：gradle 的 assets 塞得進去但沒有人看得到。
正確做法是在遊戲內的「關於」頁顯示，而那會動到呈現層——照 SDD 走，先寫規格。
還沒做的話就在發行紀錄的「未解」欄留一列，不要當作已經涵蓋。

## 三個講錯就有代價的說法

1. **不要叫它 open source。** 非商業限制不符合 OSI 的開源定義，
   對外文件、README、發行說明一律寫 **source-available** 或「專有授權」。
   講錯會讓人以為可以商用。
2. **不要把原版素材寫進授權範圍。** 「本專案授權 X」如果沒有排除原版資產，
   讀起來像在授權自己沒有的東西。條款第一條就要把界線劃掉。
3. **不要把「商業要洽談」寫成拒絕。** 條文後面加一句「歡迎來談」——
   這一條的用意是保留商業條件的決定權，不是關門。

## 想要律師擬過的標準條款時

PolyForm Noncommercial 是同一個模型（非商業免費、商業另談），
比手寫的條款穩。**要用就去官方站取全文**，不要憑記憶重打——
授權條款打錯一個字的代價和程式碼不一樣。
