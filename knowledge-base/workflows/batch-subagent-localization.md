# 批次 subagent 大規模在地化 / 內容改寫工作流

## 目的

對「幾千則、要逐則改寫」的內容(遊戲對白在地化、大量文案重寫、整庫翻譯升級)做規模化處理:用多個 subagent 平行 fan-out,同時守住**一致性、正確性、尺度**。來源:2026-07-11《幻想空間》LSL1 台式在地化,EGA+VGA 全量 3586 則、切 28 批、sonnet subagent 平行跑。與 `rulebook/45`(成本分工:粗活給便宜模型)互補——本篇是「品質控管的編排機制」。

## 何時用

- 內容 > 幾百則、且**每則都要人味/判斷**(不是機械 find-replace)。
- 要保持全域一致(譯名、術語、風格、尺度)。
- 單一 session 一則一則做太慢/太貴,但品質不能崩。

## 管線(七步)

1. **prep 切批 + 過濾**:寫個腳本抽「該改寫的行」,**跳過不可動的**——控制碼/佔位符、已保護內容(如防拷雙語問答)、純機械短字串。切 ~130 則/批。輸出每行帶「原文 + 現況」給 subagent 當底稿。
2. **试作一批,先給人看**:**別一次 fan-out 全部**。先派 1 批,把成品品質/風格給使用者確認(挑幾條 before→after),**確認風格與尺度定案後**再放其餘。省下風格歪掉才發現、白燒 N 批 token 的慘劇。
3. **共用指令檔 + 統一詞表**:寫一份 `INSTRUCTIONS.md`(風格尺度 + 硬規則 + **統一譯名/術語表**),每個 subagent 開場先 Read **同一份**。這是降低獨立 subagent 漂移的最大槓桿。
4. **fan-out**:每批一個 subagent,prompt 極簡(Read 指令檔 + 你那批 → 輸出 .done)。**用中階模型(如 sonnet)不用最便宜的**——在地化吃語感判斷,haiku 會崩;但也不必用旗艦(見 rulebook 45)。
5. **合併 + 逐行驗證(關鍵防線)**:合併腳本**逐行核對不可變欄位(查表 key / ID)一致 + 控制碼數量不變**,只替換有改的行。這道驗證會攔下任何被污染的批次。
6. **全域一致性掃描**:即使發了統一詞表,仍會漂移(同一人名出現 3 種音譯)。合併後對「可變欄位」做一次全域 replace 收斂。
7. **編碼/格式修正 + 重建 + 驗證**:改寫會引入目標編碼打不出的字(如 Big5 外字)→ 掃描 + 補 corrections 表。重建產物後**實機/端到端驗證**(非只看內部訊號,見 rulebook 65)。

## 硬規則(寫進給 subagent 的指令檔)

- **不可變欄位一字不改**(查表 key、ID、佔位符 `%s`/`\n`)——改了下游就對不上。
- 控制序列位置與數量保留;長度別暴增(有顯示上限的地方 ±30%)。
- 功能性內容別硬塞風格;有發揮空間的才發揮。
- 目標編碼打得出來的字(繁中→Big5 可編)。
- 尺度/紅線明列(涉真人政治族群、露骨程度…),先跟使用者校準(用 AskUserQuestion 定案兩三個尺度軸)。

## 踩雷(這次用 token 換來的)

- **共用 scratchpad 檔名撞車**:多個平行 subagent 若都在同一暫存目錄用同名中間檔(`col1.txt`),會互相覆寫。有的自己 diff 抓到重建,但**別依賴 subagent 自救——合併時的逐行 key 驗證(第 5 步)才是最後防線**。也可要求 subagent 用「批次唯一檔名」。
- **統一詞表發了還是會漂移**:必做第 6 步全域掃描。
- **試作沒先確認就全 fan-out**:風格/尺度歪掉要重來 N 批,最貴的錯。
- **只看綠燈不實測**:改寫完要真的重建 + 端到端跑一遍(見 rulebook 65)。
- **被保護內容誤入批次**:prep 過濾不夠嚴,防拷/雙語/特殊格式行被改寫。過濾規則要對「特徵」(含大段英文對照、選項格式、控制碼開頭)嚴格。

## 一句話

**试作定調 → 統一指令詞表降漂移 → 中階模型平行跑 → 合併逐行驗證當防線 → 全域掃描收斂 → 端到端實測。** 規模化的品質不是靠每個 subagent 完美,是靠「編排 + 驗證」兜住。
