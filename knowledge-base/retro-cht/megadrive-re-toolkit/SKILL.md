# Mega Drive 逆向工具箱

> 來源:《Might and Magic II》Mega Drive 版(EA,1991,786 KB)逆向,2026-08 實測。
> 本篇是**做一次完整的音樂逆向要走哪些步驟、每一步會怎麼靜默失敗**。

## [HARD] 音樂與場景的對照一律用反組譯推,不用人耳

**「聽起來像城鎮」不是證據。** 換一個聽的人就換一個答案,沒辦法重跑,
資料更新後也沒辦法自動驗證。要的是「程式在什麼情況下播這一首」——
那是遊戲自己的定義,而且寫成腳本之後下一個人可以重跑並推翻。

代價是要多解三層(呼叫端 → case → 曲目位址),比聽一遍慢。**接受這個代價。**
真的推不出來時,寫「未定」並說明卡在哪,**不要用聽的補上去再標成結論**——
那會讓一個猜測混進一整批已證實的資料裡,而讀的人分不出來。

完整案例:《Might and Magic II》Mega Drive 版,16 個音樂角色裡 15 個由反組譯定出,
只有 `intro` 標「未定」——它的兩個候選曲目在整片 ROM 裡都沒有呼叫端,
拿不到「什麼時候播」的證據,所以不補。

## 推導鏈(照這個順序做)

	1. 找 Z80 溝通點      掃 $A11100(BUSREQ)——所有音樂路徑的必經之地
	2. 找命令介面        movea.l #$A00000,aN 之後的 d(aN) 寫入
	3. 找播放入口        寫命令位元組之前那支上傳資料／設指標的函式
	4. 找曲目集合        用資料的自我描述結構掃全 ROM(見下)
	5. 找選曲分派        誰寫「要播哪一首」那個 RAM 變數
	6. 找呼叫端與 case   直接呼叫 ＋ **thunk 表呼叫**
	7. 給場景語意        呼叫端所屬函式 ＋ 附近的字串錨點
	8. 逐首擷取驗證      GDB stub 指定曲目,ROM 不改

### 4:曲目集合要用結構條件掃,不要靠指標表

很多遊戲沒有曲目指標表,而是資料自己帶長度或結束位址。MM2 的每首曲子
**前 4 bytes 是結束指標**,所以掃描條件是:

	u32[S-4] == E  且  S < E  且  大小落在合理範圍  且  開頭符合已知樣式

兩個獨立條件同時成立幾乎不可能是巧合。這比「找指標表」可靠,
因為指標表可能根本不存在。

### 6:[HARD] 呼叫端要連 thunk 一起掃,否則漏七成

68000 的編譯器常把跨模組呼叫走 `jsr d(a5)` 的 `jmp abs.l` 表。
MM2 的選曲分派:**直接呼叫 11 處、走 thunk 28 處**。只掃直接呼叫會得到
「只有 7 個 case 被用到」這個錯誤結論,而真相是 21 個幾乎全用到。

做法:先在 thunk 表裡找目標函式的位移,再掃 `4E AD <位移>`。

### 7:字串錨點的用法與限度

編譯器把字串資料排在使用它的程式碼附近,所以「呼叫端附近的英文句子」
可以當語意錨點。**但這是強推論不是已證實**:

- 判準是**整批一致**——戰鬥字串要聚在戰鬥 case、設施字串要聚在設施 case。
  單一一筆可能只是資料剛好排在附近。
- 老遊戲的文字常常走**索引表**(MM2 的 DOS 版與 MD 版都是),
  所以拿不到「這支函式引用了這條字串」的精確關係。要升級成已證實,
  得先解出文字索引表。
- 先掃精確引用再退回鄰近:絕對指標(`2F3C`／`4879`／`207C` 後接位址)、
  PC 相對(`4?FA` lea、`487A` pea)。MM2 兩種都幾乎零命中,才改用位置。

**跨平台印證是免費的升級**:MM2 的「地圖編號 → 區域類型」區間與 DOS 版
既有的地圖語意完全吻合,那是兩份獨立資料互相印證,可以標已證實。

### 8:[HARD] 擷取用 GDB stub,不要改 ROM

商業卡帶可能有開機完整性檢查。MM2 實測:**改動任何一個位元組(尾端
padding 除外)就開不了機**,畫面全黑,而 VGM 照樣產出 711 bytes 的驅動
初始化 —— 只看「有沒有檔案」會誤判成「錄到了但很短」。

確認方式:**改一個字串裡的字母**。純文字位元組不可能讓遊戲當掉,
掛了就是防竄改。比改程式碼再猜原因快得多。

正確做法是完全不改 ROM,用 `blastem ROM -D`(GDB remote stub,走 stdio,
不需要終端機)在執行時寫記憶體:

	?                     → S05,停在進入點
	Z0,<vblank音樂管理>,2  → 下中斷點
	c → 命中 → M <要播哪一首>,4:<曲目位址> → 重複數十幀
	m <正在播>,4          → 趁還停著驗證真的切過去
	z0 → $c#63            → 放行,這時才送錄音熱鍵

## 五種會產生假零的掃描錯誤(每一種都踩過)

| 錯誤 | 症狀 | 對策 |
|---|---|---|
| **位移當成有效位址** | 全滅,而且正對照也一起全滅 | 正對照掛掉先懷疑自己。`-$37B0(a5)` 的指令位移是 `-0x37B0`,不是 `a5-0x37B0` |
| **定址模式沒掃完** | 「沒有人寫這個變數」,而正對照通過 | 掃「延伸字等於該位移的**所有**指令」,不要列舉 `move.b dN,X` 那幾種。MM2 的 18 個寫入端全部是 `move.l (sp)+,X` |
| **只掃直接呼叫** | 只有少數 case 被用到 | 連 thunk 表一起掃 |
| **grep 反組譯文字** | 整段程式碼查無 | 裸機器碼 ROM 有大片被 IDA 留成 `dc.l`;要掃原始位元組 |
| **只掃直接寫 `($A0xxxx).l`** | 「這片沒有音樂驅動」 | 追 `movea.l #$A00000,aN` 之後的 `d(aN)` |

**零命中之前一律先做正對照**——拿同一支掃描器掃一個已知存在的目標。
但正對照只證明「你測的那一種形式」找得到,不證明你測完了所有形式。

## IDA 的三個實務問題

- **`jmp abs.l` 表會被解錯**(把 `4E F9` 之後的位址切成 `ori.b` 之類),直接讀原始位元組。
- **大片資料被併成單一陣列項**,逐位址走訪的腳本會從陣列開頭直接跳到結尾,
  症狀是「dump 出來只有兩三行」。
- **裸 68000 映像有大片區域不會被分析成程式碼**。要嘛強制 `create_insn`,
  要嘛改用原始位元組掃描。把函式邊界一次匯出成文字檔再用程式分析,
  比每次開 IDA 查一個位址快得多。
