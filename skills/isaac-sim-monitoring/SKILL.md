# Isaac Sim 監控與物理調參

## 這個 skill 要解決的問題

一般服務壞掉會噴 exception。Isaac Sim 這條鏈**不會**:

| 實際壞掉的事 | 表面症狀 | 錯誤訊息 |
|---|---|---|
| PhysX simulation view 失效 | 車永遠不動,模擬時鐘照走 | 無 |
| DDS 共享記憶體版本不相容 | ROS graph 有 tick,資料面全丟 | 無 |
| 叉齒/夾爪碰撞近似是 convexHull | 咬不進對象的孔洞 | 無 |
| 載入了舊版場景檔 | 任務「假完成」 | 無 |
| 剛體查詢對非剛體回傳未初始化記憶體 | 座標是 1e9 或 1e-41 | **`ret_val=True`** |

所以:**不要等錯誤訊息,主動去問狀態**;而且**每個數字都要知道它是從哪一層取的**。

---

## 核心原則(六條,按重要性)

### 1. 主動問,不要等報錯

在場景腳本裡開一個 UDP listener(唯讀探針),用 JSON 命令問狀態:即時位姿、碰撞近似、摩擦、材質綁定、相對某個 link 的位移。回應印到 stdout。這是 headless 環境下唯一不用附加 debugger、不影響模擬就能看到內部真相的管道。

探針的最小有用集合:

| 用途 | 回什麼 |
|---|---|
| 位姿 vs 真值 | 每個對象的 `dxy` / `dz` / `dyaw` 與 OK/OUT |
| 相對某個 link 的位姿 | 位移+旋轉的**不變量**(判斷有沒有滑動的唯一方法) |
| 物理 API 狀態 | RigidBody / Collision / Mass 有沒有 authored |
| 碰撞近似 | convexHull / sdf / … + 解析度 |
| 材質與**綁定** | 材質存在 ≠ 有生效,要看 computed binding |

### 2. 從活著的行程反查 log,不要猜檔名

同一個模擬可能被手動、看門狗、自癒腳本三種來源啟動,各寫各的檔。對著自己啟動時指定的 log 下判斷,而那支早被取代 → 讀化石。

```bash
PID=$(pgrep -f '<kit 或 python 進程特徵>' | head -1)
LOG=$(readlink -f /proc/$PID/fd/1)
stat -c %Y "$LOG"          # 最後寫入距今幾秒 —— 比內容更重要
```

前置條件:**stdout 必須落在真實檔案上**。導到 pipe 或 `/dev/null` 時這招全失效,所以啟動腳本要把輸出寫成具名檔。

同理,「現在載的是哪個場景檔」只有一種可信答案:

```bash
grep -o '/[^ ]*\.usd[a-z]*' /proc/$PID/maps | sort -u
```

不要看啟動腳本裡寫什麼——腳本會被改、旗標會覆寫。**東西不動時第一件事就是查這個 + 對 md5**。

### 3. 分清楚 authored 值、即時值、DB 值

同一個「東西在哪裡」的問題,USD authored 值(檔案裡寫死的初始位置)、物理引擎即時值、業務 DB 登記值三者可以同時存在且互相矛盾,**而且都不報錯**。

- 取即時位姿的函式若取不到,常會**靜默退回 authored 值**。一定要讓它標記自己用了哪個後端,判讀前先確認。
- 拿 authored 值當即時值 → 把「正在動」讀成「不動」,這是誤診的常見起點。
- 驗收要**雙軌**:DB 帳面 + 物理座標。兩邊都單獨說過謊。

### 4. 查詢成功 ≠ 值可用

物理引擎的剛體查詢對**非剛體**(例如 articulation 的根 Xform)會回「成功」但內容是未初始化記憶體。必做合理性檢查:

```python
if not all(math.isfinite(v) for v in pos + quat):        return False
if max(abs(v) for v in pos) > SCENE_SCALE_LIMIT:         return False   # 場景約 ±20m → 取 500
n = math.sqrt(sum(q*q for q in quat))
if not (0.5 < n < 2.0):                                   return False   # 垃圾四元數范數≈0
```

不擋就會把垃圾座標餵給跟車鏡頭與量測工具,全程無錯誤。

### 5. 接觸問題:先查幾何,再查材質

薄板(叉齒、夾爪指)用 `convexHull` 近似會被補成**實心楔形**,根本咬不進對象的孔洞。這種狀態下無論怎麼調摩擦,都只是在補償一個幾何錯誤,最後得到一堆「有效但說不出為什麼」的魔數(例如 μ=5.0 這種非物理值)。

改成 SDF 之後,實測放置 yaw 誤差從 0.3~1.1° 降到 0.1°。

順序:**碰撞近似 → 質量/慣量 → 接觸/求解器參數 → 摩擦**。

### 6. 「我設了這個參數」≠「這個參數生效了」

真實案例:團隊長期以為抓握靠 μ=5.0 高摩擦材質撐住。離線解析 USD 才發現那個材質**根本沒有 authored 的摩擦值**,而且補綁邏輯早就被停用——抓握**完全來自** SDF 碰撞近似,摩擦那條線從頭到尾沒接上。

把功勞歸給沒生效的改動,是最貴的一種錯覺:下次照抄必失敗,而且會反覆調一個不存在的旋鈕。

所以每次調參後**都要回頭驗證它真的掛上了**:材質存不存在(一個檢查)+ 碰撞體有沒有綁到它(另一個檢查),兩個都要看。

## 判讀:三個容易讀錯的量

### 漂移 vs 途中滑動 vs 放置誤差

這是三件不同的事,要用不同方法量:

| 現象 | 怎麼量 | 訊號 |
|---|---|---|
| **放置誤差** | 動作結束後量一次 vs 真值 | 單點 `dxy` / `dyaw` |
| **途中滑動** | 搬運**過程中**連續取樣「相對承載 link 的位姿」 | 不變量若**單調漂移** = 真的在滑;**不變** = 沒滑,別去動摩擦 |
| **累積漂移** | 跨多輪量同一個真值偏差 | 斜率,不是單點 |

> 通則:懷疑「過程中」的現象,就不能只在「結束後」量。使用者說「邊走邊歪」時,收工後的單次量測永遠證不出來。

累積漂移常有**正回饋**機制:插入行程固定,對象若已偏深就被頂得更深 → 每輪 +5~10 cm,五六輪後就叉不到了。單輪數字看不出來,一定要跑耐久測試看斜率。

### 連續取樣要用位元組偏移

log 一天能長到幾百 MB,每輪 `tail -n 100` 是 O(檔案大小),取樣頻率會被自己拖垮。記偏移只讀新增段:

```bash
OFF=$(stat -c %s "$LOG")
while ...; do
  send_probe
  sleep 1.5
  NEW=$(stat -c %s "$LOG")
  [ "$NEW" -gt "$OFF" ] && { tail -c +$((OFF+1)) "$LOG" | grep -F '<標記>'; OFF=$NEW; }
done
```

### 同名欄位不同語意 → grep 一定要先鎖行別

一支探針常會連帶跑別的檢查,而兩者印出同名欄位(都叫 `dxy`)但量的是不同東西。不鎖行別就會把「途中經過某處的距離」當成「漂移」,結果是**每趟都誤觸自動修復**。

```bash
grep -oE 'dxy=[0-9.]+'                      # ❌
grep -F '[check_place]' | grep -oE 'dxy=…'  # ✅
```

## A/B 試驗紀律

調參必然要 A/B。把一輪標準化成:寫旗標檔 → 重啟模擬 → 等就緒 → 跑一輪 → 收判定。

**判定一律取地面真相**,不看畫面、不看任務佇列狀態:

| 判定 | 怎麼取 |
|---|---|
| 有沒有真的移動 | TF `world→base_link` 最遠距離超過門檻 |
| 對象有沒有真的被搬走 | 即時世界座標位移超過門檻 |
| 任務終態 | DB 最後一筆的狀態 |
| 控制器 | 有沒有送出軌跡、有沒有 ABORT |

三個踩過的坑:

1. **等「就緒」不能用 `tail -N` 比對日誌**——上一輪殘留的「已就緒」會讓等待提前放行,模擬還沒起來就開始量測。要記行號,只認之後新增的行。
2. **每輪先重載看門狗**。防抖計數多半是記憶體變數,重啟才歸零;否則連做幾輪就撞到「1 小時 N 次」上限卡住。
3. **A/B 前先確認沒有同時改別的東西。** 看似廢話,但已經因此浪費過整輪測試——結論歸給 A,實際上 B 也動了。

## 快速體檢清單

東西不動 / 沒被搬走 / 數字很怪時,照這個順序:

1. 各元件 PID 在不在?log **最後寫入距今幾秒**?
2. `/proc/<pid>/maps` — 載的是哪支場景檔?md5 對不對?
3. 即時位姿的 **backend 是哪一層**?(是即時值還是 authored fallback)
4. 物理 API(RigidBody / Collision / Mass)在不在?
5. 碰撞近似是什麼?材質綁上了嗎?
6. ROS/中介層:TF 有沒有更新?控制器有沒有送軌跡?
7. 業務 DB vs 物理座標雙軌對照。

**前六項全綠但東西還是沒動** → 懷疑傳輸層靜默丟資料(DDS 共享記憶體版本不相容是實際踩過的一次:graph 有 tick、topic 列得出來、資料面全丟,修法是強制走 UDP-only profile)。

## 調參流程

```
① 先建可重跑的 pass/fail 訊號   ← 沒有這個就不要開始調
② 量 baseline(至少 3 輪 —— 單輪數字沒有意義,漂移會累積)
③ dump 現況:碰撞近似 + 摩擦 + 材質綁定
④ 一次只改一項 → A/B → 量同樣的訊號
⑤ 判讀:是真的變好,還是這輪運氣好?3 輪內的差異多半是噪聲
⑥ 改動落回腳本,帶 .bak-before-<主題>-<日期>
⑦ 回頭驗證「這個參數真的生效了」(見原則 6)
```

## When NOT to apply

- 只是要跑既有場景、不碰物理參數也不除錯 → 照 runbook 走就好。
- 有 GUI 可用且問題肉眼看得出來 → 先看畫面,不必先架探針。
- 問題明確在業務層(排程、派工、API)且物理已驗過 → 這裡的方法不會幫到你。
