# 復古 remake：挑來源版本、位元組簽章、找缺口的三種方法、模擬器只做驗證

> 觸發：新 remake 專案有多個平台版本要挑主要來源；規則文件要能指回原版位元組；
> 「還缺多少功能」盤點；拿模擬器對拍畫面；規則解出了卻不確定實作有沒有接上。
> 來源：SunDog remake（Apple II → Atari ST，2026-08）的兩份專案內經驗文件。專案專屬的位址、
> 常數、格數都留在專案內，這裡只留規則。

> 一手資料贏二手與文件衛生（[`rules/63`](../../rules/63-truth-in-code-not-stale-markers.md)）、便宜模型抽斷言核實（[`rules/45`](../../rules/45-model-cost-division-of-labor.md)）、

## 一、挑主要版本：先問「遊戲邏輯能不能靜態讀成規則」

多個平台版本並存時，第一個判準不是哪個最經典、哪個畫面最好，而是**程式碼的形式**。

| 形式 | 能做到什麼 | 成本形狀 |
|---|---|---|
| p-code／腳本／bytecode（UCSD、SCUMM、AGI、Infocom…）| 有現成反組譯器就能整份讀成規則，每條規則釘一段位元組 | 讀一次就是一條規則，線性且便宜 |
| 原生機器碼（6502、Z80、8086…）| 要靠模擬器 watch、反組譯 + 溯源，一次證實一個字串或一個位址 | 每條結論都要跑模擬器，成本線性但係數大得多；IDA 環境本身也可能卡住 |

**做法**：每個版本各花半天，確認「反組譯出來的東西能不能直接讀成規則」。能的當規則與資料的
來源；其餘版本各自找到能貢獻的面向（畫面、英文文字、另一份獨立資料、紙本地圖）當**交叉
oracle**，並在 worklist 明寫「它證實哪些斷言、不證實哪些」，其 `unknown` 是該來源的邊界不是
專案的待辦。SunDog 的 Apple II 六天解出載入鏈與畫面緩衝，Atari ST 六天解出世界表、對話與
價格公式——差在形式，不在努力。

這一步排在 [`reverse-engineer-retro-game-remake`](../../reverse-engineer-retro-game-remake/SKILL.md) 的指紋辨識之前；指紋辨識
（`retro-toolchain-runtime-fingerprinting.md`）是「這個版本裡哪些是玩家碼」，本節是「哪個版本
值得當來源」。

## 二、位元組簽章：每一條規則都要能指回磁碟上的一段位元組

**規則：規則文件裡的每條語意對應一段位元組簽章；工具要求它在整份映像裡恰好出現一次，
落點等於段基底加段內位址，對不上就 fail-closed。**

- 簽章擋兩種錯：位址記錯，以及換了一份磁碟卻沿用舊結論。它不證明語意對（語意靠讀取端與
  實跑），但保證「你說的那段碼」真的在那裡。與 [`rules/64`](../../rules/64-re-screenshot-oracle.md)（拿已知輸出反推資料位置）是
  姊妹技法：64 從畫面找位置，簽章把找到的位置釘死。
- 產出分兩層：**JSON 是工具重產的證據**（簽章、位址、hash、輸入檔的 hash），**同名 .md 是人寫
  的語意**。要問「這條規則憑什麼」只看這兩份，不看記憶、檔名、美術字樣。改語意先改工具再
  重產，不手改 JSON。
- typed consumer 載入時驗簽章與落點；內嵌副本要與 docs 版逐位元組相同，並有測試守著
  （否則會出現「JSON 更新了但程式用舊副本」）。
- 生成檔裡的 `openQuestions`／`unresolved` 和規則表一樣會過期：解掉一個欄位就順手改它，
  盤點前先清掉已解掉卻沒改的，否則盤點建立在過時標記上。
- 簽章對版本敏感（工具鏈指紋文件裡對版本簽章的警告同樣適用）：換版本要重釘，
  不能沿用。

## 三、找缺口要用原版自己的清單，而且要三種方法一起用

**規則：「還剩多少沒解」與「還缺多少功能」是兩個問題，用同一份清單回答會漏掉後者。**

1. **原版自己的段落／符號字典當完整清單**。手冊列的子系統對完了，仍會漏掉手冊沒列的整段
   玩法（SunDog 漏了四個 segment）。自己的筆記只會列「已經在解的還剩多少」。
2. **證據 JSON 逐條對程式碼核實**（配 `rules/63`、`45`）：規則解出來、簽章釘好了，實作
   仍可能漏接或接錯。訊號常常很小：一個永遠播不到的音效、一個沒讀的 `div 32`、一行沒有註解
   自陳理由的常數。
3. **原版實跑**：前兩種是靜態的；只有跑起來才發現開局會重擲、空船不會遇敵這類「規則有讀到
   但沒想到要接」的東西。

三種各自找到不同的缺口，做完一種不代表清單完整。

## 四、模擬器狀態只做驗證；對拍要從快照解幀，不是截圖

**收斂句：模擬器裡看到的位址、快照、VRAM、截圖，只能用來證實或推翻一個關於原版檔案的斷言，
不能成為 remake runtime 的資料模型、規則輸入、存檔欄位或素材管線。**
（分散在 `rules/64`、[`retro-hardware-spec-first`](../retro-cht/retro-hardware-spec-first/SKILL.md)「量測是對帳不是依據」
與 `knowledge-base/retro/` 各平台文件——這裡只收斂，不重寫細節。）

對拍畫面的四個做法：

- **畫面從記憶體快照的顯示記憶體解出來，不用截圖**。截圖與存快照之間差幾秒，會動的東西
  （敵艦、公轉）就對不上；同一份快照同時含 VRAM 與變數，解幀後兩者是同一瞬間。
- **種點法**：要量「某段程式擦掉哪一塊」，把快照 VRAM 裡那一帶的空白像素點亮再還原，第一幀
  裡消失的像素就是被塗掉的區域。比等一張剛好有星點落在框裡的畫面快。
- **對畫面一律用執行時的記錄，不用出廠值**：出廠資料可能在開局被重擲、被夾限；配不上時先
  讀 RAM 裡的記錄。
- **全域位址用磁碟上已知的固定資料反推**：拿一段確定的常數（樣板列、名稱表）掃 RAM，
  找到陣列就反推出全域基底，再算出其他變數的位址；不要猜隔壁。

輸入驅動的坑要寫進工具 README，不是留在對話裡：相對滑鼠頂到螢幕邊界會靜悄悄停住、
游標要閉迴路定位（歸零→換算→回授）、存快照的指令在目標檔還在時可能跳 stdin 提示卡死整個
模擬器（先刪檔再輪詢 log，不用固定 sleep）、機器被別的容器分走 CPU 時固定等待時間不夠。

## 五、原版素材：「repo 不收」與「runtime 從哪裡讀」是兩件事

- **repo 與發行包不收原版位元組**——這條是共識（[`remake-architecture`](../../reverse-engineer-retro-game-remake/references/remake-architecture.md)、
  `rules/85`）。
- runtime 的形狀有兩種，都合法，要在 READY spec 明寫選哪一種：
  - **每次啟動從玩家自己的原版檔即時解碼**（SunDog：`-atari-disk`、`sundog-sound-export`）。
    沒給檔案時要一樣完整可玩（用自己的美術）；解碼器要 fail-closed，換一份不同的磁碟就拒絕。
  - **一次性解碼成 remake 自有的自包含資產**（[`dragon-wars-cht-remake`](../retro-cht/dragon-wars-cht-remake/SKILL.md) 的走法）。
  差別在授權（自包含資產是不是衍生物）與玩家體驗（要不要自備檔案），不是對錯。

## 六、「刻意不照做」獨立列區；remake-owned 是會過期的標籤

- 解出來但不照做的項目集中一區，每列寫「原版怎麼做／remake 怎麼做／為什麼」；還沒解出來的
  另一區。兩區不能混，也不能留在正文當「自有規則」。
- `remake-owned` 的定義是「原版對應的程序沒解出來或不適用」——它有有效期：解出來那一刻就
  要改成上面兩區之一。SunDog 多數早期標成 remake-owned 的項目，原版其實都寫得很清楚。
- 兩種 remake-owned 理由不同，要寫對：「呼叫端還沒追」與「那個東西原版根本不存在」不是同
  一件事。
- 這一條併進 `retro-remake-spec-gated-workflow.md` 的「已知差異」：差異要標理由類別與到期
  條件。

## 七、「量不到」先懷疑走錯路，再懷疑機率

**規則（配 [`rules/40`](../../rules/40-learning-loop.md)、[`41`](../../rules/41-whack-a-mole-stop-rethink.md)）：連續兩輪同類失敗，先回頭讀原版的分派表，不要再抽樣。**

SunDog 三個案例的共同點：「按住沒反應」「擲骰不中」「掃描沒命中」都是量法或前提的問題
（走錯選單、貨艙是空的、站位其實是查表），改參數重試只是抽樣，讀一次分派表就結案。

## 八、一手資料推翻二手推論：這些形狀要認得

原則在 `rules/63`；這裡只補 SunDog 又收到的形狀：

| 二手 | 一手 |
|---|---|
| 檔名與外觀（「那條圖是按鈕列」）| 逐格對表（是以編號索引的圖示表）|
| 文件裡的一句話（投影的 y 號）| p-code 的那條分支＋實跑十二個點 |
| 常數的直覺解讀（「x 座標」）| 每個都等於折線的位元組數減一 |
| 出廠值（「開局各漂 ±1」）| 執行時記錄（累加重擲，可以差四格）|
| 索引欄位（「改索引就能換城市」）| 資料是初始化時載進緩衝的 |

文件裡寫錯的一句最危險：remake 會照抄它，測試會把錯的釘住。

## 九、打包與錄影的容器坑（案例，通則見 `rules/35`）

- 容器以 root 寫過的輸出目錄，之後用自己的 UID 重跑會**靜默失敗**——錄影腳本十二段「秒過」
  一個檔都沒更新。重跑用新目錄，或一開始就以目前 UID/GID 跑。
- 不要用 `timeout` 砍主機端的合成腳本：容器裡的 ffmpeg 留下來，下一輪跟它搶中間檔。
- README 截圖要不要更新，用重拍逐像素比對決定：0 像素差就不動；差很多就追原因，截圖也是會
  過期的斷言。
