# 復古遊戲 remake 通用作業法則

本文件整理《大富翁2》逆向、重寫、對拍、多語系、音畫、跨平台打包與收尾過程中，
可以跨專案沿用的方法。它不是 Rich2 規則規格，也不把本作的位址、常數或素材格式
外推到其他遊戲；專案專屬事實仍應回到各自的原始檔、反組譯資料庫與實機 oracle。

本版只保留下一個 remake 可直接採用的工作順序、證據契約與交付閘門。Rich2
儲存庫內的 `docs/lessons.md` 另保存「錯誤如何形成」及具體事故，不是本通則的
執行前置，也不應把其中的專案狀態帶到其他遊戲。

## 1. 先定義完成，再開始解

「遊戲能跑」「remake 內部測試全綠」「近似可玩」與「嚴格原版 parity」是四種不同
狀態。開工時先建立唯一現況表，至少分成：

| 狀態 | 必要證據 | 不能宣稱什麼 |
|---|---|---|
| 可啟動 | 正常入口、素材載入、第一個可操作畫面 | 核心規則正確 |
| 可玩 | 正常玩家路徑能開始、移動、決策、存退讀與結束 | 所有原版細節一致 |
| 近似完成 | 預先定義的抽樣、平台與硬閘門通過 | unknown 已變成 confirmed |
| 嚴格 parity | 同狀態原版 oracle、規則／畫面／動畫／音訊逐項收據 | 硬體逐週期一致，除非真的量過 |

完成定義必須先固定；不能等做到某個程度後，再挑一套剛好會通過的指標。

## 2. 每項結論使用固定證據契約

一項可被後續實作採用的結論，至少要同列：

1. 輸入檔名與 SHA-256；
2. 工具與版本；
3. 位址空間及原始定位（檔案偏移、segment:offset、IDA linear address 等）；
4. 原始 bytes、交叉參照、資料 diff、實機截圖或可重播操作；
5. 語意；
6. 證據等級：已證實、強推論、假說、未知；
7. 玩家體驗是否受影響，以及是否阻擋目前交付。

工具內改名只能協助導覽，不能取代原始位址。沒有寫證據等級的漂亮名稱，最容易在
幾週後被誤當成已證實事實。

## 3. 先辨識工具鏈，再解玩法

大量未知函式出現時，先辨識 compiler、linker、runtime、packer、DOS extender、
圖形／音訊 driver 與 middleware。做法是以 bytes、呼叫者分布、失敗 consumer、
module 邊界和字串簽章交叉判讀，而不是只看函式序言或高 fan-in。

這一步能避免三種浪費：

- 把 stack probe、浮點模擬器或陣列 runtime 當成未還原玩法；
- 用未知函式數量冒充 remake 完整度；
- 因錯認 compiler 家族，將其他工具鏈的 helper 名稱套到本作。

只能證明家族時就只寫家族；copyright 年份或相容 pattern 不足以鎖定精確版本。

## 4. 逆向結論必須經過規格閘門

正式行為採用以下單向流程：

```text
原始證據 → DRAFT 規格 → 證據審查 → READY
         → typed 實作 → 同狀態驗證 → CONFORMED
```

- probe、記憶體注入與 direct-entry 可以縮小問題，但不能直接成為產品路徑；
- 實作中遇到新 unknown，退回 RE／spec，不用「看起來合理」補洞；
- 規格要寫輸入、前置狀態、順序、公式、輸出、副作用、存檔語意與證據等級；
- 同一條規則只保留一份正式定義，其他文件用連結引用。

## 5. 用垂直鏈驗證，不用孤立 helper 宣告完成

每個玩家功能至少追通一條完整鏈：

```text
原始 bytes／素材
  → parser 與邊界驗證
  → typed data
  → 規則與亂數消耗
  → UI／動畫／音訊
  → 存檔與重載
  → 正常玩家路徑收據
```

只解出資料表、只寫規則函式、只畫出畫面，或只補 direct-entry 測試，都不能單獨算
功能完成。若遊戲有快速／戰術、玩家／AI 或桌面／手機等雙路徑，至少各抽一條主要分支。

## 6. 格式解碼要同時證明形狀、內容與消費端

副檔名、檔案大小可整除或 magic 相似，只能提出候選格式。可靠的格式結論需要：

- 多個真實樣本，而非只看一檔；
- count、offset、stride、界限與完整消耗不變量；
- malformed input 失敗即關閉；
- atlas、文字 dump、波形或存檔 diff 等可視化；
- 至少一個遊戲 consumer 能正確讀取；
- 可寫格式要做 byte-for-byte round-trip，未知區域原樣保留。

同一副檔名可能包不同容器；選 decoder 應依檔頭與驗證結果，不依副檔名猜測。

## 7. 不要把規則狀態與呈現狀態壓成一個欄位

復古棋盤、地圖或交通工具動畫常同時存在：

- 邏輯格號／節點；
- 真實顯示座標；
- 動畫起點、端點與子像素進度；
- 朝向與交通工具相位；
- 鏡頭原點；
- 停車後的持久方向。

這些欄位若混用，常出現「先往後退再前進」「先橫移」「停車後方向跳回預設」「鏡頭
過早追人」等看似動畫 polish、實際是架構錯誤的症狀。通則是：規則先產生路徑與終態，
呈現層保存真實起點並逐段播放；動畫完成後只提交已確定的終態，不從座標重新猜方向。

## 8. 事件生命週期與執行順序要成為資料

同格多事件、兩階段新聞、問答、卡片、主播與回場流程，不能靠 UI callback 的偶然順序。
每個事件應明示：

1. 觸發與決策發生在移動前、途中或落地後；
2. 同格事件的優先序；
3. 每一頁／階段的輸入閘門；
4. AI 倒數何時重啟；
5. 音樂是否延續、cue 是否等待播放完成；
6. 何時允許存檔、離開或恢復；
7. 每個階段只執行一次的識別碼。

生命週期應能序列化或留下 continuation token；否則手機暫停、重連或存讀檔很容易
重放付款、跳頁或漏事件。

## 9. 原版對拍必須先做到同狀態

相同 seed 不保證相同亂數序列；不同 compiler runtime、亂數演算法或開機消耗都會讓
第一回合分岔。可靠對拍要固定：

- 原版／remake 版本與雜湊；
- 城市、角色、日期、資產、格號、顯示座標、方向；
- RNG 狀態或可證實的輸入映射；
- 畫布、色盤、鏡頭、動畫相位與輸入序列。

無法固定時，必須標成 nearby-state、layout-only 或玩家觀感比較，不能寫 pixel-perfect。
畫面主要骨架相似也不能補足狀態不同。

## 10. 畫面、動畫與音訊分開驗收

### 固定畫面

- 保留未縮放的原版與 remake PNG；
- 先確認裁切、畫布與整數最近鄰縮放，再算矩陣；
- 同時保存差分圖、色盤索引差異、狀態 metadata；
- 不用遮罩把動態差異偷偷排除，除非規格事先定義並揭露。

### 動畫

- 總幀數正確不代表每一段位移都播放；
- 驗起點、每段端點、停留、朝向、遮擋順序、鏡頭與完成閘門；
- 固定抽幀之外還要看連續影片，因為「每張都合理、接起來很怪」很常見。

### 音訊

- 分開驗 cue 選擇、觸發順序、sample duration、循環點、音量與播放完成閘門；
- 技術上可解碼不等於人耳確認；
- DOS PCM／DAC／PIT／DMA 或 OPL wall-clock 若只剩硬體逐週期差異，採公開規格與成熟
  模擬器的可重現近似，標為 hardware-spec approximation，不讓硬體考古無限延伸。

## 11. 多語系是版面與資產問題，不只是翻譯表

每個玩家可見文字都應走同一語意鍵與排版入口，包括 F1 Help、圖片按鈕覆蓋文字、
主播槽、卡名、設定選單和錯誤訊息。每個欄位定義文字安全矩形、字型、基線、最大行數、
截斷／換行策略與最長實際字串測試。

烙在原始圖片裡的文字要先分類：

- 原作識別或美術字：可明示保留；
- 實際操作按鈕：需要可替換文字層或各語資產；
- 無法安全重畫：在文件揭露，不要假裝已完整在地化。

每種語言都要以正式字型、正常玩家路徑和原生邏輯解析度截圖驗收，不能只看字串表。

## 12. 正常玩家路徑是不可替代的最後 oracle

自動測試至少需要一條不用傳送、強制事件、賜予資源或 forced-win 的垂直路徑：

```text
啟動 → 新遊戲 → 移動 → 決策／事件 → 存檔 → 離開 → 重載 → 中後期／結局
```

direct-entry 適合診斷孤立畫面；它不能證明入口可達、狀態準備正確、回場完整或存檔能
恢復。長局模擬也不能取代真人 UI：兩者測的是不同失敗面。

## 13. 抽樣完成門檻必須預先登記且保留硬失敗

如果專案接受近似完成，可以採分層玩家情境通過率，但必須在執行前固定：

- 抽樣單位、分層、最低配額與獨立性；
- 每個情境的通過／失敗判準；
- 版本、seed、平台、資料雜湊與證據位置；
- 統計方法與信心水準；
- crash、卡死、存檔損壞、素材外洩、核心規則違反等零容忍硬閘門。

Rich2 採單側 95% Clopper–Pearson 下限 ≥99%，299 個全數通過才剛越過門檻；這是本作
裁決，不是所有 remake 的固定數字。通則是：不能刪除失敗樣本後重算，也不能讓平均
通過率抵銷災難性失敗。

## 14. 授權必須分離程式碼、原版素材與第三方依賴

程式碼授權只涵蓋權利人有權授權的部分，不會自動授權原版 ROM／資料檔、商標、美術、
音樂、字型或轉檔後的 OGG／PNG。發布前建立三份清單：可公開、僅本機、來源未知而拒絕。

若採標準授權：

- 官方文本逐字使用，不混入自訂條款；
- 署名與必要 notice 放獨立檔；
- README 說明人類可讀摘要、商業聯絡與原版素材排除；
- 每一個 ZIP、AppImage／安裝包與 APK 都實際包含授權文件；
- 掃描器無法識別壓縮檔或轉檔音訊時，另做內容清單驗證。

Rich2 選用 PolyForm Noncommercial 1.0.0 是專案裁決，不應自動套用到其他 remake。

若目標同時是「靠 remake 累積名聲」與「保留程式碼的商業權利」，標準的非商業條款不夠：
它不會主動允許實況／影片／報導（開分潤的影片照字面就是商業使用），也沒有貢獻回授，
日後要商業授權得逐一找貢獻者同意。這種情況用自訂條款，至少要有四段：
明示允許的傳播（含平台分潤）＋署名、保留權利與雙授權、貢獻回授含商業條件、
點名 repo 裡踩在原版素材上的東西（截圖、原版字串、量測表）。
範本與各條理由見 [`retro-remake-license-v2.md`](../retro/retro-remake-license-v2.md)，
規則在 `rules/85`。

## 15. 打包成功不等於平台驗收

每個目標至少分四層：

1. 可重現編譯；
2. 封包結構、檔名編碼、權限與授權文件；
3. 容器內啟動 smoke、素材載入、音訊路徑與存檔位置；
4. 真機輸入、音訊、視窗／觸控、暫停恢復與安裝生命週期。

Linux 產物不能替代 Windows／macOS 真機，能產 APK 也不能替代 Android 的旋轉、返回、
TalkBack、process death 與音訊生命週期。交付時保存 SHA-256、內容清單、建置 HEAD、
驗證報告與已知未驗項。

含原版素材的本機完整版與公開引擎包必須使用不同目錄和不同流程；不要期待 deny-list
替你辨認 ZIP 內或 OGG 中的原版內容。

## 16. 推廣片也是驗收產物

推廣片應由目前引擎重新擷取，不沿用舊幀代表新版；至少包含正常遊玩、已支援語言、
Help／設定等宣稱功能。完成後：

- `ffprobe` 驗 codec、解析度、fps、聲道、取樣率、時長；
- `volumedetect`、`blackdetect`、`silencedetect` 驗非靜音、無削波、無長黑／長靜音；
- 每一幕中心抽幀做接觸表並逐張目視，不能用等間隔抽樣漏掉短分幕；
- 原版畫面與 remake 畫面標清狀態關係；
- 原版音樂即使轉成 OGG 仍是原版素材，公開權利必須獨立判斷。

## 17. Docker 可重現性與主機衛生是產品品質的一部分

建置、測試、轉檔、DOSBox、IDA、FFmpeg 與 GUI 自動化都應在鎖版容器內：

- 一次性容器使用 `--rm`、資源上限與預設 `--network none`；
- 原始資料唯讀掛載，寫入容器指定目前 UID/GID；
- 工具 image 先沿用既有版本，缺件才修可重現來源；
- 每批工作後查執行中／停止容器、輸出擁有權與專案 dangling image；
- 環境失敗與產品失敗分開記錄，再用同一容器、同一命令乾淨重跑。

「換到主機直接跑一次」會讓成功收據失去可重現性，也容易污染其他專案。

## 18. 文件必須按責任分工，否則完成項會復活

建議只保留以下角色：

- `README`：用途、操作、目前摘要、下載／驗證入口；
- `CONTEXT`：唯一現況與已推翻斷言；
- `WORKLIST`：尚可執行的工作與完成條件；
- `WORKLOG`：按時間保存命令、收據、失敗與勘誤形成史；
- `docs/re`：如何查到；
- `docs/spec`：正式行為契約；
- `docs/playtest`：原版／remake 實跑證據；
- `docs/lessons`：錯誤模式。

新增證據時先修現行正文，再追加歷史勘誤；不要只在另一份文件說「舊結論錯了」，卻讓
原斷言繼續被索引和交接引用。

## 19. 停止條件：玩家可見證據足夠後就回到產品

逆向採「可玩性優先、證據最小充分」：一條玩家功能已有原始輸入、typed model、規則、
UI、存檔與正常路徑收據後，就停止逐行翻譯無關 helper。只有新發現會改變玩家體驗、
資料安全或目前交付 gate 時，才重新開啟 RE。

compiler runtime、檔案服務、初始化樣板、標準硬體時序與沒有玩家 consumer 的 linked
support，保留最小定位與 unknown／不阻擋說明即可。完整不是「每個 byte 都取名字」，
而是所有宣稱都有足夠證據，所有玩家必要路徑都有可重播結果。

## 20. 可直接套用的里程碑清單

### 開工

- [ ] 固定原版輸入、雜湊、版本與唯讀來源。
- [ ] 建立證據等級、位址空間與文件責任。
- [ ] 定義近似完成、嚴格 parity、停止線與素材政策。
- [ ] 指紋辨識 compiler／runtime／packer／driver。

### 每個功能

- [ ] 原始資料或控制流證據。
- [ ] READY 規格。
- [ ] typed parser／state／rule。
- [ ] UI、動畫、音訊與順序。
- [ ] 存檔／恢復。
- [ ] 正常玩家路徑與至少一條相鄰失敗分支。
- [ ] 同狀態原版比較或明示近似邊界。

### 發行前

- [ ] 全庫測試、靜態檢查、語系與素材 deny-list。
- [ ] 各平台編譯、封包內容、權限、授權與啟動 smoke。
- [ ] 公開包與本機原版素材包完全分離。
- [ ] 推廣片由目前版本重拍並完成影音與逐幕目視驗收。
- [ ] SHA-256、build HEAD、內容清單、已知限制與真機缺口齊全。
- [ ] 工作樹、檔案擁有權與 Docker 容器清理狀態確認。

這套方法的核心不是追求最多文件或最多函式名稱，而是讓每一個玩家可見宣稱都能沿著
「原始證據 → 規格 → 實作 → 正常路徑 → 交付收據」反向追溯。
